# Phase 1b-3a: Shopify Connection Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the hard gates the 1b-2 review left open: bind the OAuth callback to the user who started it, purge a shop across all orgs on `shop/redact`, stop keeping webhook payloads, and enforce one active org per shop in the database.

**Architecture:** Shopify redirects to a Next route handler in the web app, which forwards the raw query string and the user's session to a new authenticated API endpoint that performs the existing completion steps plus a user and role check. A new definer function purges every disconnected or errored connection of a shop. The receiver stores empty payloads. A partial unique index backs the "one org per shop" rule.

**Tech Stack:** TypeScript strict, NestJS 11, Drizzle 0.45, Postgres RLS, Next.js 15 (App Router, route handlers), Vitest 5, BullMQ (worker).

**Spec:** `docs/superpowers/specs/2026-10-08-phase1b3a-hardening-design.md` (the spec is the authority; where this plan refines it the Global Constraints say so).

## Review Focus

Failure modes the spec implies that need explicit tests (each is pinned in the task named):
1. A different signed-in user (or a user who is no longer admin) completing someone else's OAuth state must connect nothing and burn the state — Task 5.
2. A signed-out user must end on the login page and come back to the callback with the Shopify query string intact — Task 7.
3. A `host` parameter containing `=` padding or other encoded characters must verify whether Shopify signs the raw encoded query or the decoded values — Task 1.
4. A shop connected in two orgs (one disconnected, one errored) plus an active reinstall in a third: only the first two are purged — Task 2.
5. Two orgs connecting the same shop at the same moment: exactly one succeeds — Tasks 3 and 5.
6. No webhook body of any topic survives in the database — Tasks 3 and 6.

### Task 1: `verifyOAuthRawQuery` and a raw signing helper

**Files:**
- Modify: `packages/connectors/src/shopify/hmac.ts`, `packages/connectors/src/testing/signing.ts`
- Test: `packages/connectors/test/shopify-hmac-raw.test.ts`

**Interfaces:**
- Produces: `verifyOAuthRawQuery(rawQuery: string, apiSecret: string, opts?: { now?: Date; maxAgeSeconds?: number }): boolean`. The old object form `verifyOAuthQuery` stays until Task 5 removes it. In `@erq/connectors/testing`: `signOAuthRawQuery(params: Record<string, string>, secret: string, mode?: 'encoded' | 'decoded'): string` returns a query string (no leading `?`) with `hmac` appended last.
- Behaviour: strip one optional leading `?`; reject empty input, input over 4096 characters, a pair without `=`, a repeated key (compared after URL-decoding the key), a missing or non-hex `hmac` (64 hex digits). Remove the `hmac` pair, sort the remaining pairs by key, and accept if the HMAC-SHA256 (hex) matches EITHER (a) the pairs joined with `&` exactly as received (encoded), OR (b) the pairs rebuilt from URL-decoded keys and values joined with `&` (the representation the 1b-2 code used). Comparison is constant-time on equal-length buffers; both candidate comparisons are always evaluated (no early exit that leaks which matched). The timestamp rules are unchanged (`timestamp` must be a safe integer, at most 60 s in the future, at most `maxAgeSeconds` default 600 old). Why both: Shopify's documentation does not say unambiguously whether the signature covers the encoded or decoded values; accepting either is safe (a valid HMAC under the secret authenticates the same logical parameters either way) and the code comment says to drop one after the first real install.

In `hmac.ts` add:

```ts
const MAX_QUERY_LENGTH = 4096;

function hmacHexEquals(candidateMessage: string, apiSecret: string, given: Buffer): boolean {
  return safeEqual(createHmac('sha256', apiSecret).update(candidateMessage).digest(), given);
}

/**
 * Verifies the signature Shopify puts on the OAuth redirect, from the RAW query string.
 * Shopify's docs do not say whether the signed message uses the encoded or the decoded values, so both are
 * accepted (a valid HMAC under the app secret authenticates the same logical parameters either way).
 * After the first real install, drop whichever form Shopify does not use.
 */
export function verifyOAuthRawQuery(
  rawQuery: string,
  apiSecret: string,
  opts: { now?: Date; maxAgeSeconds?: number } = {},
): boolean {
  const query = rawQuery.startsWith('?') ? rawQuery.slice(1) : rawQuery;
  if (!query || query.length > MAX_QUERY_LENGTH) return false;
  const seen = new Set<string>();
  let hmac: string | undefined;
  const encoded: { key: string; pair: string }[] = [];
  const decoded: { key: string; pair: string }[] = [];
  let timestamp: string | undefined;
  for (const pair of query.split('&')) {
    const eq = pair.indexOf('=');
    if (eq <= 0) return false;
    let key: string;
    let value: string;
    try {
      key = decodeURIComponent(pair.slice(0, eq).replace(/\+/g, ' '));
      value = decodeURIComponent(pair.slice(eq + 1).replace(/\+/g, ' '));
    } catch {
      return false;
    }
    if (seen.has(key)) return false;
    seen.add(key);
    if (key === 'hmac') {
      hmac = value;
      continue;
    }
    if (key === 'timestamp') timestamp = value;
    encoded.push({ key, pair });
    decoded.push({ key, pair: `${key}=${value}` });
  }
  if (typeof hmac !== 'string' || !/^[0-9a-f]{64}$/i.test(hmac)) return false;
  const bySortedKey = (a: { key: string }, b: { key: string }) => (a.key < b.key ? -1 : a.key > b.key ? 1 : 0);
  const given = Buffer.from(hmac, 'hex');
  const matchEncoded = hmacHexEquals(encoded.sort(bySortedKey).map((p) => p.pair).join('&'), apiSecret, given);
  const matchDecoded = hmacHexEquals(decoded.sort(bySortedKey).map((p) => p.pair).join('&'), apiSecret, given);
  if (!(matchEncoded || matchDecoded)) return false;
  const ts = Number(timestamp);
  if (timestamp === undefined || !Number.isSafeInteger(ts)) return false;
  const nowSec = Math.floor((opts.now ?? new Date()).getTime() / 1000);
  return ts <= nowSec + 60 && nowSec - ts <= (opts.maxAgeSeconds ?? 600);
}
```

/** Returns a query string (no leading `?`) with `hmac` appended, signed over the encoded or decoded values. */
export function signOAuthRawQuery(
  params: Record<string, string>,
  secret: string,
  mode: 'encoded' | 'decoded' = 'encoded',
): string {
  const keys = Object.keys(params).sort();
  const enc = (s: string) => encodeURIComponent(s);
  const message = keys
    .map((k) => (mode === 'encoded' ? `${enc(k)}=${enc(params[k]!)}` : `${k}=${params[k]}`))
    .join('&');
  const hmac = createHmac('sha256', secret).update(message).digest('hex');
  return [...keys.map((k) => `${enc(k)}=${enc(params[k]!)}`), `hmac=${hmac}`].join('&');
}

RETURNS void
LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public, pg_temp AS $$
DECLARE v_shop text; v_platform store_platform;
BEGIN
  SELECT external_account_id, platform INTO v_shop, v_platform FROM store_connections
   WHERE org_id = p_org_id AND id = p_connection_id;
  IF NOT FOUND THEN
    RETURN;
  END IF;
  -- The ledger is delete-restricted for app_user and restricted by foreign key; this is the one intended removal path.
  DELETE FROM inventory_movements m USING locations l
   WHERE m.org_id = p_org_id AND l.org_id = p_org_id
