# Phase 1b-2: Shopify Connection (design)

Date: 2026-10-06
Status: draft for review
Builds on: `2026-10-06-phase1b1-sync-foundations-design.md` (merged). Follows CLAUDE.md sections 6.1, 6.3 and 9.

## 1. Purpose and scope

Phase 1b is split into four sub-projects: 1b-1 sync foundations (done), **1b-2 Shopify connection (this spec)**, 1b-3 Shopify sync (products, costs, locations, inventory, orders including POS, backfill, webhook-triggered syncs), 1b-4 costs and import (CSV, manual cost entry, Products and pricing screen).

1b-2 lets a signed-in owner or admin connect a Shopify store to an org, keeps the access token encrypted, receives and stores Shopify webhooks, and implements Shopify's mandatory privacy webhooks and uninstall handling. It does **not** fetch any Shopify data (1b-3).

Decisions made with the owner (2026-10-06):
- No Shopify Partner app or dev store exists yet. Everything is built to Shopify's documented contracts and verified with fixtures and a fake Shopify behind an injected HTTP client. Live verification happens later.
- Scope includes the API and one minimal "Connect Shopify" card with a status row in the web app. The onboarding wizard and a full connections settings page are later work.
- Webhooks are verified, stored (deduplicated), acknowledged immediately, and processed by a worker job. 1b-2 acts on `app/uninstalled` and the privacy topics only. Order, product and inventory topics are stored for 1b-3.

Out of scope: any data fetching, any live Shopify call, CSV import, cost entry, onboarding wizard, billing, customers table, other platforms.

## 2. Architecture

Approach A: platform logic lives in `packages/connectors/src/shopify` and has no framework or database dependency. All network calls go through an injected `HttpClient` interface. The NestJS API owns routing, auth, org checks and persistence. The worker owns webhook processing. No Shopify-specific field leaves `packages/connectors`.

```
web  --POST install-->  api  --builds authorize URL, stores oauth_state-->  browser -> Shopify
Shopify --redirect--> api /callback  --verify, consume state, exchange code (HttpClient)-->
        encrypt token (AAD connection:<id>) -> store_connections (active) -> register webhooks -> redirect to web
Shopify --webhook--> api /webhooks/shopify --verify HMAC on raw body, insert webhook_events (dedupe), enqueue--> 200
worker: webhook job -> topic handler (uninstall, privacy; data topics stay 'received')
```

### 2.1 `packages/connectors/src/shopify` (pure)
- `isValidShopDomain(shop)`: lowercase `[a-z0-9][a-z0-9-]*\.myshopify\.com`, nothing else (no path, port, userinfo, uppercase, trailing dot, look-alike hosts).
- `buildAuthorizeUrl({ shop, apiKey, scopes, redirectUri, state })`.
- `verifyOAuthQuery(query, apiSecret)`: HMAC-SHA256 over the sorted query string without `hmac`, hex, constant-time compare, `timestamp` freshness window.
- `verifyWebhookSignature(rawBody, hmacHeader, apiSecret)`: base64 HMAC-SHA256 of the raw bytes, constant-time compare, malformed or missing header returns false.
- `exchangeCodeForToken(http, { shop, apiKey, apiSecret, code })`: POST to the shop's access token endpoint, returns `{ accessToken, scopes }`, maps HTTP failures to typed errors (`AuthError`, `TransientError`, `PermanentError`), never includes the response body or secret in messages.
- `registerWebhooks(http, { shop, accessToken, topics, callbackUrl })`: idempotent (a subscription that already exists is success). Exact mechanism (Admin API subscriptions versus app configuration) is confirmed against Shopify's current documentation during implementation and noted in a code comment with the doc link; topics configured with the app (privacy topics, `app/uninstalled`) are not registered per shop.
- `ShopifyWebhookHeaders` parsing: `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic`, `X-Shopify-Shop-Domain`, `X-Shopify-Webhook-Id` (used as the dedupe key; `X-Shopify-Event-Id` is stored when present).
- Config object: `{ apiKey, apiSecret, scopes, redirectUri, webhookUrl }` built by the API from env, validated with zod.
- Default scopes are the read-only set 1b-3 needs (products, inventory, locations, orders). Protected customer data is not requested in 1b-2.

### 2.2 Database (migrations 0013+, generated by drizzle-kit; RLS and definer functions in custom migrations)
- `oauth_states` (tenant table): `id`, `org_id`, `user_id`, `platform`, `shop`, `nonce_hash` (SHA-256 of the nonce, the plain nonce exists only in the redirect), `expires_at` (10 minutes), `consumed_at`.
- `webhook_events` (tenant table): `id`, `org_id`, `store_connection_id` (composite `(org_id, id)` FK), `topic`, `external_event_id`, `payload` (jsonb), `received_at`, `processed_at`, `status` (`received`, `processing`, `processed`, `failed`, `ignored`, `deferred`; `deferred` means a data topic parked for the 1b-3 sync pipeline), `error` (sanitized), unique on `(org_id, store_connection_id, external_event_id)`.
- Pre-org lookups need SECURITY DEFINER functions (four in total, listed below), because the OAuth callback and the webhook receiver have no org context. Each pins `search_path = pg_catalog, public, pg_temp`, revokes EXECUTE from PUBLIC, anon and authenticated, and is granted only to `app_user`:
  - `app_consume_oauth_state(nonce_hash)`: atomically marks an unexpired unconsumed state consumed and returns `(org_id, user_id, shop)`; returns nothing otherwise.
  - `app_find_store_connection(platform, external_account_id)`: returns `(org_id, connection_id, status)` only.
  - `app_list_stale_webhook_events(older_than, limit)`: used only by the worker's sweep. Returns `(org_id, event_id)` for events `received` since before the cutoff (never queued) and, since migration 0016, `processing` events whose `updated_at` is before the cutoff (a worker crashed). Never an API route.
  - `app_purge_store_connection(org_id, connection_id)`: used only by the worker's `shop/redact` handler (never an API route). Deletes the connection's data in dependency order (movements, levels, refund lines, refunds, order lines, orders, listings, locations, cursors, sync runs, webhook events, oauth states, the connection itself), writes an `audit_log` row, and touches nothing outside that org and connection. This is the only intended path that removes `inventory_movements` rows (the ledger is otherwise delete-restricted since 1b-1).
- `connection_status` already has `disconnected`. No enum change.
- Both new tables get `app_secure_tenant_table`, isolation-suite fixtures and composite FKs per the project rules.

### 2.3 API (`apps/api/src/connections`)
All routes except the two public ones apply `AuthGuard`, `OrgGuard`, `RolesGuard` in that order.
- `POST /orgs/:orgId/connections/shopify/install` (owner, admin): body `{ shop }` (zod, validated with `isValidShopDomain`). Lazily deletes expired states for the org, stores a new state, returns `{ authorizeUrl }`. 503 `shopify_not_configured` when env is missing; the app still boots.
- `GET /connections/shopify/callback` (public): verifies the query HMAC and shop, consumes the state via `app_consume_oauth_state`, exchanges the code, then inside `withTenant(orgId)` upserts the `store_connections` row for `(org, shopify, shop)` (a reinstall or reconnect updates the same row, resetting status to `active`, clearing `last_error`), stores the encrypted token (AAD `connection:<id>`) and scopes, registers webhooks, writes an audit row, and redirects to the web app with `?shopify=connected` or `?shopify_error=<code>` (short, fixed codes: `invalid_request`, `state_expired`, `shop_mismatch`, `shop_in_use`, `exchange_failed`, `not_configured`, `server_error`). `shop_in_use` means the shop is actively connected to another org; `server_error` is any unexpected failure. The API reads `REDIS_URL` (optional) and enqueues webhook jobs with BullMQ; without it events stay `received` and the worker sweep picks them up.
- `POST /webhooks/shopify` (public): requires raw body capture for this route only. Verifies the signature, resolves the connection through `app_find_store_connection`, inserts the event with `ON CONFLICT DO NOTHING` under `withTenant`, enqueues a `webhook` job when newly inserted, always returns 200 for a verified request (including duplicates and unknown topics), 401 for a bad or missing signature, 200 with nothing stored for an unknown shop (so Shopify does not retry forever; logged without payload).
- `GET /orgs/:orgId/connections` (any member): platform, shop, status, `last_synced_at`, `last_error`. Never returns credentials or scopes secrets.
- `POST /orgs/:orgId/connections/:id/disconnect` (owner, admin): status `disconnected`, token wiped, pending syncs not enqueued, audit row. Never deletes the row.

### 2.4 Worker (`apps/worker/src/webhooks`)
A `webhook` queue job carries only `{ orgId, eventId }` (no payload, no credentials) validated with zod. The handler loads the event under `withTenant`, claims it (`received` or `failed` to `processing`, or a `processing` claim older than 10 minutes, compare-and-set; the claim commits before the work), and dispatches by topic:
- `app/uninstalled`: connection to `disconnected`, token wiped, audit row; event `processed`.
- `customers/data_request`, `customers/redact`: we hold no customer PII (orders carry only an opaque external customer id), so the event is marked `processed` with a note. Handler lives behind a single function so Phase 2 can extend it when a customers table exists.
- `shop/redact`: calls `app_purge_store_connection`.
- Order, refund, product and inventory topics: event becomes `deferred` (1b-3 consumes them); unknown topics `ignored`.
- Failures mark the event `failed` with a sanitized message and rethrow for BullMQ retry; the handler is idempotent (a `processed` event is a no-op).

### 2.5 Web (`apps/web`)
One "Connect Shopify" card on the post-onboarding page: shop-domain input with inline validation, calls install, redirects to `authorizeUrl`. A status row lists connections (Connected, Needs attention with the plain-English reason and a reconnect action, Disconnected) with last synced. Loading skeleton, empty state explaining the next step, error banner from `shopify_error` codes. WCAG AA, keyboard navigable, mobile layout checked. Reconnect reuses the install flow.

## 3. Security rules specific to this sub-project
- The OAuth state is single use, bound to org, user and shop, hashed at rest, expires in 10 minutes. The callback never trusts an org or user from the query.
- All HMAC comparisons use constant-time compare on equal-length buffers.
- The shop domain is validated before any URL is built or any request is made (no open redirect or SSRF to arbitrary hosts).
- Tokens exist in memory only during the callback; they are never logged, put in URLs, job data, `last_error` or audit metadata. A sanitizer strips tokens and secrets from any error text before it is stored.
- Webhook payloads are stored but never logged. Events are tenant data under RLS.
- `app_purge_store_connection` and the other definer functions must never be wired to an API route; the definer owner must be superuser or BYPASSRLS (as for the existing functions). Documented in `docs/architecture/tenancy.md`.
- Config secrets come from env only and are listed in `.env.example` with placeholders.

## 4. Errors
OAuth failures redirect with a fixed error code and never expose internals. Token exchange maps to `AuthError`, `TransientError` or `PermanentError` as in 1b-1. Webhook ingestion is idempotent and fast (verify, one insert, enqueue). If enqueue fails after the insert, the event stays `received` and a sweep in the webhook job scheduler (registered with the existing `resume-stalled` style scheduler) re-enqueues events `received` for more than 10 minutes for the topics 1b-2 handles.

## 5. Testing
- `packages/connectors`: unit tests for domain validation (including look-alike hosts and unicode), authorize URL, OAuth query HMAC (valid, tampered, missing, replayed timestamp), webhook HMAC (valid, tampered body, wrong secret, missing and malformed header, constant-time helper), token exchange with a fake `HttpClient` (success, 401, 5xx, malformed body, no secret in errors), webhook registration idempotence.
- `packages/db`: RLS and fixtures for both tables, isolation suite, dedupe uniqueness, definer functions (grants, `search_path`, consume is single use and cannot be replayed, find returns ids only, purge deletes only the target connection's data including ledger rows, leaves other connections and tenants untouched, writes the audit row, `app_user` still cannot delete movements directly).
- `apps/api`: end to end through a fake Shopify: install, callback (success, bad HMAC, expired, reused and mismatched state, reconnect updates the same row), webhook receiver (valid, duplicate, bad signature, unknown shop, raw body integrity), connections list (no credentials), disconnect, role checks (viewer and analyst denied), not-configured behaviour.
- `apps/worker`: handlers with in-memory fakes and the embedded database: uninstall, both customer topics, shop/redact, data topics stay received, idempotent replays, failure marks event failed. Queue tests that need Redis are skipped without Docker.
- `apps/web`: unit tests cover the pure helpers (error messages, relative time, connection view); the Playwright path (guided empty page, error-text safety) runs only in CI. Phone-width layout is unverified.

## 8. Success criteria
1. A fake-Shopify end-to-end test connects a store, stores an encrypted token, and the connections list shows it without credentials.
2. Bad signatures, replayed or expired states, mismatched shops and invalid domains are all rejected with tests.
3. Duplicate webhooks are stored once; uninstall and all three privacy topics are handled; `shop/redact` removes the connection's data (ledger included) without touching anything else.
4. The isolation suite passes with both new tables; lint, typecheck and tests pass in every package; Redis-dependent tests are skipped and listed as unverified.
5. The embedded-Postgres leak is fixed (no orphan `postgres` processes or `erq-pg-*` directories after a test run).
